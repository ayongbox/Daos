# ADR-0003 部署形态：模块化单体

- 状态：已接受
- 日期：2026-11-16
- 关联功能：F05-03、F05-05、F06 相关集群能力的边界
- 前置：ADR-0001、ADR-0002

## 背景

需要确定社区版首发是模块化单体、微服务，还是内核加插件，并说明商业版如何演进。约束条件：

- 社区版单机 Docker Compose 部署，目标 4C8G；
- 并发 200 用户、50 并发写，单表 ≤500 万行；
- 元数据发布涉及 DDL 执行，事务与版本一致性要求高；
- 会话、文件、调度锁、缓存已约定走抽象接口。

## 决策

**采用模块化单体：单进程、单 JVM、Maven 多模块，模块边界由 ArchUnit 强制。**

```text
一个可执行进程 daos-web
├── daos-core      契约与编译
├── daos-runtime   数据服务与流程
├── daos-license   授权
└── daos-ext-*     SPI 装配，可选
```

理由：

1. 首发要能在一台 4C8G 机器上跑通完整闭环，微服务的注册中心、网关、链路追踪、分布式事务会把部署复杂度推高一个量级；
2. 元数据发布要同时完成「版本快照 + DDL 迁移 + 缓存失效 + 流程定义校验」，单进程内是一段本地事务 + 幂等补偿，拆成服务后必须引入分布式事务；
3. 租户上下文、权限快照、渲染树编译都依赖同一份元数据，单进程可保证读一致性；
4. 模块边界已经用依赖方向与 ArchUnit 固化，未来拆服务的成本是「搬运模块」，不是重写。

## 备选方案

| 方案 | 弃用原因 |
|---|---|
| 微服务 | 社区版自托管部署过重；跨服务事务与租户上下文透传成本高；无规模收益 |
| 内核 + 插件运行时 | 社区扩展已通过 SPI 装配，核心模块不需要热插拔；引入类加载隔离会破坏契约可预测性 |
| 纯单体单模块 | 无法强制边界，商业扩展会渗透社区代码，违反开源边界 |

## 集群与拆分的演进路径

- 社区版：单实例，会话、文件、调度锁、缓存走抽象接口的本地实现；
- Plus：同一构件横向扩展多实例，抽象接口切到 Redis / 对象存储 / 数据库锁，不修改业务代码；
- 企业版：按模块边界拆 `runtime` 与 `web` 为独立服务，`core` 作为共享契约库，接口不变。

## 后果

- 单进程是扩展上限的来源，垂直扩展与读写分离是首发唯一手段，需在验收基线内明确；
- 任何「模块内直接调用另一模块 infra」的写法都视为越界，由 ArchUnit 拦截；
- 定时任务、事件投递需默认单实例安全（本地锁），集群化时替换为分布式实现；
- 本决策变更需重新评审阶段 0 契约，不得在实现阶段临时改为微服务。
